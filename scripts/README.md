# Migration scripts

`bun run build` runs Vite directly. It does not execute any of the historical source-patching scripts below. The workflow is read-only and fails if install or build changes tracked files or creates unignored files.

## Final migration tooling

### `build-storage-manifest.mjs`

Read-only local helper for the final migration package. It scans downloaded Storage bytes and writes a deterministic JSON manifest containing relative paths, byte sizes and SHA-256 hashes.

Usage:

```bash
node scripts/build-storage-manifest.mjs <storage-root> [output.json] [source-name] [bucket]
```

Example source names: `lovable-prod`, `hom-r-office`. The default bucket is `firmen-dateien`.

This script has no Supabase credentials and performs no network writes.

### `migrate-storage.mjs`

Historical guarded uploader only. It uses one fixed owner UUID and fixed historical object counts. Do **not** use it as the final two-source Storage merge tool without regenerating and reviewing its manifest from the actual downloaded source bytes. `upsert: false` prevents silent overwrite, but that alone is not sufficient for the final reconciliation.

See `../MIGRATION_PACKAGE.md` for the final reproducible package and `../MIGRATION_CLOUDFLARE.md` for the cutover gates.

## Historical source-patching scripts

The scripts below are retained as historical evidence and must not be run as a build or final migration step.

| Script | Review outcome |
| --- | --- |
| `sync-main-final-fixes.mjs` | Calendar fixes and the Fahrtenbuch Excel sheet are now in source. Standalone PDF generation and the staging PWA guard were already in source. |
| `finalize-navigation-ui.mjs` | Navigation changes are now in source. A link from the Fahrtenbuch export page to trip/vehicle management preserves editing access. |
| `cleanup-kalkulation-ui.mjs` | Never wired into the current build. Retained and **not executed**: its removal of tender-document state/UI would discard a main feature; its alternate Fahrtenbuch navigation also conflicts with the final navigation script. |

Routes are generated by TanStack Start. The migration routes are included in the committed `src/routeTree.gen.ts`. Generate and commit route changes during development; CI must never commit them back automatically. Disabling the Start route crawler was tested and rejected because the framework requires its crawl result during builds.

No script or workflow added by this cleanup deploys to Cloudflare, applies SQL, modifies Production, changes DNS, or shuts down Lovable.

## External photo-retention cron safety

The migrations beginning `20260813000703` and `20260831203604` use `cron.schedule_in_database(..., database := current_database(), active := false)`.
The job is created inactive in a single statement, with no committed active window. The original schedule and HTTP command are retained; creating the job does not execute that command. Neither migration activates it.

Activation is a separate administrative action requiring explicit approval. Before activation, verify and replace any historical runtime URL and verify the credentials against the approved target. Do not activate this job during migration validation.

Changing these historical files affects fresh replays only; it does not alter jobs in databases where the migrations were already applied. No existing project is updated by this source documentation.

Read-only verification after replay:

```sql
SELECT jobid, jobname, active
FROM cron.job
WHERE jobname = 'foto-retention-taeglich';
```

The expected result is one row with `active = false`.
